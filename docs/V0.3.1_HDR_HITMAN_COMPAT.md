# UniversalDLSS5 v0.3.1 HDR / Hitman compatibility pass

This update treats display color space as part of the swapchain contract rather than assuming every DXGI backbuffer is SDR.

## HDR detection

UniversalDLSS5 queries `IDXGISwapChain3::GetColorSpace1()` on the active swapchain and combines it with the backbuffer format and observed HDR10 metadata. `Auto` therefore follows the game swapchain, not the monitor's advertised HDR capability or the Windows desktop toggle.

Recognized paths:

- SDR sRGB / SDR UNORM
- HDR10: `R10G10B10A2_UNORM` with PQ / BT.2020 color space
- scRGB: `R16G16B16A16_FLOAT` with linear `G10` / Rec.709 color space

When a 10-bit swapchain supplies HDR10 metadata during a mode transition, that metadata is also treated as strong HDR10 evidence unless the user explicitly chose **Force SDR**.

Unsupported HDR contracts are bypassed rather than processed with an incorrect transfer function.

## HDR neural proxy

The game HDR signal is not sent to the verified Feature-18 path as raw PQ/scRGB values. The bridge:

1. decodes HDR10 PQ/BT.2020 or accepts linear scRGB;
2. keeps a linear FP16 working image;
3. tone-compresses a bounded paper-white proxy for the neural pass;
4. applies a bounded neural detail/tone ratio back onto the original high-range linear image;
5. re-encodes to the original HDR10 PQ/BT.2020 or scRGB swapchain contract.

This keeps the existing Feature-18 UNORM input/output contract while preserving the game's HDR highlight range outside the neural proxy.

## Fullscreen / Alt-Tab transitions

The bridge hooks:

- `SetFullscreenState`
- `SetColorSpace1`
- `SetHDRMetaData`
- `ResizeBuffers`
- `ResizeBuffers1`

A color-space or HDR-mode transition resets the neural/color pipeline and requires four stable Presents before processing resumes. This is intended for games such as Hitman that recreate or retag their swapchain when entering fullscreen, HDR, or returning from Alt-Tab.

The attach log records the detected encoding, DXGI format, color-space id, metadata state, and peak luminance whenever this contract changes.

## NVIDIA driver guard

The direct in-game signed Feature-18 route has a conservative guard for NVIDIA user-mode driver file versions `32.0.16.1664` and `32.0.16.1686`, which have been reported by another Feature-18 implementation as D3D12 crash-risk routes. On those exact versions UniversalDLSS5 prefers the Streamline DLSS-NR path and refuses the direct route unless **Attempt unsupported hardware** is explicitly enabled.

This is a narrow compatibility guard, not a claim that every crash on those driver branches has the same cause.

## Device-loss diagnostics

If `Present` returns an error, the bridge records both the Present HRESULT and `GetDeviceRemovedReason()` in the attach log. The controller diagnostics also expose those values on a subsequent status update.

For a Hitman test, leave **Color pipeline = Auto**, **Frame pacing = Synchronized**, and **Neural passes = 1x** first. The diagnostics should identify the actual swapchain format and color space before moving to additional passes.

## D3D12 temporal-resource lifetime safety

A separate crash-risk found during this pass was unrelated to HDR itself: setting Motion to **Zero** previously stopped the shader from using native motion but the D3D12 bridge could still wrap a captured game motion texture through D3D11On12. The same was true for ephemeral NGX inputs whose lifetime was not guaranteed through Present.

The v0.3.1 compatibility path now touches native game motion only when **Motion = Auto**, honors **Use game depth**, and consumes captured D3D12 guides at Present only when the provider marks them valid through Present. Short-lived NGX inputs are retained as diagnostics only until a safe same-command-list snapshot path is available. This makes the Zero-motion / no-game-depth test a real isolation test rather than merely changing the later shader route.
