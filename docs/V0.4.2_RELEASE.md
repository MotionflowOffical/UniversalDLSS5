# UniversalDLSS5 v0.4.2

v0.4.2 focuses on late-attached D3D12 recovery stability and automatic cleanup when a target application exits.

## D3D12 recovery transport

The `ModernD3D12Recovery` route no longer creates the external-host shareable color texture through a D3D11On12 device. Recovery now:

- keeps D3D12 swapchain copies on the same proven game DIRECT queue inferred from real PRESENT transitions;
- waits on per-game-queue fence points before touching the current backbuffer;
- creates the full-resolution recovery color surface as a shareable D3D12 committed resource;
- opens that resource on a separate D3D11 device created on the same physical adapter with `ID3D11Device1::OpenSharedResource1`;
- explicitly proves D3D12 pre-copy completion before D3D11 uses the shared color surface;
- explicitly proves D3D11 completion before D3D12 performs the post-copy;
- continues to isolate Feature 18 through the x64 NRHost in recovery mode.

This change targets the `DXGI_ERROR_ACCESS_DENIED` device-removal failures observed in late-attach D3D12 recovery. Exact swapchain-creation-queue D3D12 and native D3D11 routes are unchanged.

## Automatic application-exit detach

Injected bridges now maintain a renderer-activity heartbeat from DXGI, D3D9, OpenGL, and Vulkan presentation hooks. After the target process has previously owned a real top-level game window, the bridge automatically begins normal teardown when that window disappears and rendering has remained silent for five seconds.

This prevents the bridge worker thread from keeping a game process/module mapping alive after the application has closed. The controller also clears stale attachment state when its tracked application processes disappear.

The existing quiescent detach rules remain in force: if complete hook teardown cannot be proven safe, the bridge still prefers `DetachedResident` over force-unloading live hook state.

## Compatibility status

The classic D3D9 / x86 -> x64 NRHost path retains the v0.4.1 Feature-18 contract fixes. Native D3D11 and exact-queue native D3D12 frames remain isolated from compatibility overhead.

There is no screen-capture fallback and Feature-18 color input/output is not intentionally downscaled.

v0.4.2 remains experimental and requires runtime validation on Windows.
