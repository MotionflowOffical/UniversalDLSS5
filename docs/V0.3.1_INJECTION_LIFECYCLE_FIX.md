# UniversalDLSS5 v0.3.1 injection lifecycle fix

This patch addresses crashes that occur before `attach-<PID>.log` can be created.

The previous injector used a fixed 10-second wait for the remote `LoadLibraryW` thread, did not check whether the wait timed out, then read `STILL_ACTIVE` (259) as a non-zero success value and freed the remote DLL-path buffer even though the target loader could still be reading it.

The v0.3.1 lifecycle is now:

1. Create `inject-<PID>.log` before opening the target.
2. Resolve the address of `LoadLibraryW` relative to the module that actually owns the local function and map the same RVA into the target process.
3. Start remote `LoadLibraryW` and wait without freeing its path buffer until the remote loader thread has definitely completed. The injector also watches target-process termination.
4. Confirm the bridge module by enumerating the target modules instead of interpreting the truncated remote thread return value as an HMODULE.
5. Resolve the exported `UniversalDLSS5_BridgeStart` RVA and invoke it in a second remote thread.
6. `DllMain` performs only minimal module bookkeeping; it no longer creates the bridge worker thread while the Windows loader lock is held.
7. The controller waits briefly for the injector. If loading remains in progress, it reports `injection pending` and keeps the target reserved so maintenance cannot repeatedly reinject it.

Logs are written to `%LOCALAPPDATA%\\UniversalDLSS5\\logs` and are available before bridge startup, so pre-bridge failures can now be diagnosed.
